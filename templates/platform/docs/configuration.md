# Configuration — @@PROJECT@@

Three kinds of configuration meet in this repo, and keeping them apart is what makes it safe
to read:

1. **Declared, committed values** — what runs, at which version, with which settings. They are
   the bundle and its `values/` files, reviewed like code. There is no separate configuration
   format to learn: the bundle *is* the configuration.
2. **Secret references** — committed, but they carry a *path*, never a value. The External
   Secrets Operator resolves them in-cluster.
3. **Credentials** — never committed and never in this repo at all. This document names
   **where each one originates**, which is the part that makes an environment rebuildable by
   someone who was not there when it was first built.

## Declared values (committed)

Precedence, lowest to highest — one direction, no exceptions, because a second direction is
what makes "where does this value come from" unanswerable:

```
chart defaults
  → bundle globals        (namespace, imageRegistry, publishDomain, vaultPathPrefix)
    → values/common.yaml  (every chart in THIS environment)
      → values/<name>.yaml (one component)
```

Dicts merge recursively; everything else replaces. **Lists replace rather than concatenate** —
with append semantics a list set in `common.yaml` could be added to but never shortened, so an
environment could not opt out of anything it inherited.

| Value | Where it lives | Why there |
|---|---|---|
| What runs in an environment, and at which version | `clusters/<cluster>/environments/<env>/bundle.yaml` | The single file a release touches. One file to review, one file to revert. |
| Namespace, registry, publish domain, secret path prefix | bundle top level → passed to every chart under `global` | They come from the bundle rather than from a values file so an environment cannot accidentally point at another environment's registry or secret path. |
| Defaults for every chart in an environment | `values/common.yaml` | Resource requests, pull secrets, anything true of the whole environment. |
| One component's settings | `values/<name>.yaml` | The filename **is** the bundle entry name — `validate-bundles.py` reports an unreferenced file as dead, because a values file that applies to nothing is invisible otherwise. |
| Raw resources that are not a service chart | `clusters/<cluster>/environments/<env>/manifests/<component>/` | Database clusters, topics, `ExternalSecret`s. One directory per component, so deleting a component deletes its resources. |
| Reconcile interval | `interval` in the bundle | Applied to every generated resource, so one environment cannot drift to a different reconcile cadence than its own bundle claims. |
| What this platform needs from the cluster | `requirements.yaml` | A demand on another team. Not a value this repo sets — a value it checks. |

Two things that deliberately have **no home here**: cluster-wide components (cert-manager, the
CNI, the gateway — they belong to the infra repo, see [architecture.md](architecture.md)), and
any chart's *implementation*. This repo configures charts; it does not contain them.

## Secret references (committed) — values (never)

An `ExternalSecret` names a path in the store; the operator resolves it into a `Secret` in the
namespace. What is committed is the path, and the path is namespaced by the environment:

```
{vaultPathPrefix}/{path}      # dev/sql, dev/message-bus, dev/llm …
```

`vaultPathPrefix` comes from the bundle, so **a dev bundle structurally cannot read production
keys**. That is a property of the layout rather than a permission someone must remember to
configure — which matters, because the failure mode of the permission-based version is silent
and only visible in an audit log nobody reads.

Two provisioning shapes, and picking the wrong one is how a credential ends up existing in one
place only:

- **Pull from the store** — anything a human or another system creates: registry credentials,
  third-party API keys. The value is put into the store by the documented procedure below.
- **Generate in-cluster, then push** — anything with no external source: service-to-service
  tokens, database passwords. Generated by the operator and written back to the store, so both
  sides read the same value and a rotation has exactly one origin.

**No secret value is ever committed, not even briefly, not even in a values file that "will be
fixed before merge".** A secret that reached a remote branch is compromised even after a
force-push; gitleaks runs in CI and as a pre-commit hook for exactly this reason.

## Credentials — where each one comes from

| Credential | Used for | Origin | Lifetime |
|---|---|---|---|
| kubeconfig (human) | `check-requirements.py`, reading state back, `flux diff` | Issued by the infra repo's bootstrap; kept in the operator's `~/.kube/`. Never in this repo — `.gitignore` carries patterns so a stray copy cannot be committed. | rotate on staff change |
| `E2E_KUBECONFIG` (CI) | the manual `e2e` job only | A read/test-scoped kubeconfig for ONE non-production environment. Protected + masked CI variable. Never cluster-admin, never the reconciler's own credential. | rotate on staff change |
| Registry pull secret | pulling images **and** OCI charts | Provisioned by the infra repo into the workload namespace **and** the Flux namespace. Referenced here by name (`imagePullSecret`), never created here. | rotate quarterly |
| Secret-store credentials | everything the platform runs | Resolved in-cluster by the secrets operator from `ClusterSecretStore`. This repo commits paths only. | per the store's policy |
| Service-to-service tokens, DB passwords | inside the platform | Generated in-cluster and pushed to the store. Nobody types them, so nobody has to rotate them by hand. | on demand |

If a credential is missing, the fix is a ticket in the repo that owns it — the infra repo for
anything cluster-level — citing the `@@PREFIX@@` id. It is never a value pasted into a values
file to unblock a deploy.

## CI variables

| Variable | Set where | Notes |
|---|---|---|
| `RUNNER_TAG` / `RUNNER_TAG_INFRA` | group or project CI settings | Consumed by the shared templates' runner anchors. `.gitlab-ci.yml` overrides both anchors with a literal tag — GitLab does not expand nested variable references in `tags`. |
| `E2E_KUBECONFIG` | project CI settings, protected + masked | See above. Absent by default: the `e2e` job fails loudly rather than passing without having run. |
| `NO_LINT_CHECKS` | ad hoc | Skips `yamllint` for an urgent fix. It does **not** skip `standard-drift` or `doc-sync`, deliberately — those cannot be "wrong about an environment". |
| `SAST_DISABLED` | set to `"false"` in `.gitlab-ci.yml` | gitleaks is the scanner that matters most here. Leave it on. |

## Adding a new environment

1. Copy the nearest existing environment directory; do **not** start from an empty one — the
   omissions are what bite, and they are silent.
2. Set `name` (it must contain the environment directory name — promotion relies on that
   correspondence), `namespace`, `vaultPathPrefix`. Each must be unique: two environments
   sharing a namespace overwrite each other's releases, which is why
   `validate-bundles.py` checks it across files.
3. Seed the secret store under the new prefix **before** the first reconcile, and verify the
   cluster with `check-requirements.py`.
4. Record it in [environments.md](environments.md) — including who may approve a deployment
   into it. An environment that exists but is not in that table is one nobody knows the rules
   for.
